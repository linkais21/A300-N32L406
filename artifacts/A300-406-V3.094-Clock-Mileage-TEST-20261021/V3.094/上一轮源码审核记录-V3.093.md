## 3. 代码质量与架构

本轮删除了只在启动阶段使用、又被 `jt808_init` 同步复制的一份永久终端描述副本，改为启动局部变量。最终静态 RAM 实际减少 104 B，最大前台调用栈增加 8 B，完整运行间隙净增加 96 B。

项目已使用 `-Os`、LTO、函数/数据独立 section、链接 GC 和精简格式化器。保留调试信息用于最终链接栈审计，调试 section 不进入烧录 BIN。经隔离比较，加入 `-fno-caller-saves -fno-schedule-insns2` 后，修复后的候选满足容量门禁。这是体积优化结果，不能推导 CPU 速度提升；执行周期变化需上板测量。

没有为缩小代码删除校验、超时、鉴权状态、掉电事务、日志或恢复路径。其他试验配置中存在体积增大或溢出，未采用。异常策略和启动身份检查仅同步已复核源码指纹，4096 B 安全间隙、库代码证明和未知调用拒绝条件保持原值。

重复/无效代码审核的处理原则及结果：

- 启动终端副本属于可确认消除的重复驻留数据，已处理。
- libgcc 中同地址的别名不是两份实际代码，不能重复计算其占用。
- 供应商驱动及未引用函数的 section 已可被链接 GC 丢弃；删除源文件中的未引用函数并不必然节省当前镜像。
- 调试串口格式化与有界缓冲格式化具有不同输出语义，没有机械合并。
- AGNSS 4096 B 流工作区已按所有权复用；网络接收、注入阶段和诊断工作区的生命周期不同，不能仅按数组大小重叠或缩小。

维护性风险集中于 `main.c` 的跨模块调度、`ec800m.c` 的多事务/URC 分流、`jt808.c` 的协议与轨迹调度，以及 `blind_zone.c` 的事务恢复。它们需要按状态和资源所有权维护；本轮不做大范围结构重写。大函数的最终符号尺寸含 LTO 内联结果，不等于原始函数单独占用。

## 5. CPU、响应时间与长期运行

当前是前台协作状态机加中断交接架构，没有 RTOS。UART/GNSS ISR 主要负责接收和轻量事件交接；Flash 擦写及协议业务在前台进行。异常栈审计覆盖当前 NVIC 分组和优先级，未修改中断策略。

仍存在明确的前台阻塞：TCP 发送可等待提示 3 秒和发送确认 5 秒；NTP 一次等待最长 10 秒；同步 UDP 诊断的开通、发送、关闭等待可累计到秒级。等待钩子只推进 GNSS 接收解析，没有运行完整轨迹过滤、里程和工作模式调度。因而持续网络故障时可能出现轨迹采样间隙或弯道里程低估风险；现有有界等待并不等于实时性达标。

建议在后续资源腾挪后，将日志 UDP、NTP 和发送事务逐步改为可取消的协作状态机，并设定每轮处理字节/时间预算。不要在等待钩子中直接调用完整主循环，否则可能引入重入、Flash owner 争用和栈增长。

串口 115200、8N1 下，100 字节线速发送约 8.68 ms；这是传输下界，不是 CPU 使用率。ISR 最长时间、关中断区间、Flash 擦写时的串口丢字节、签名验签耗时和主循环最大间隔均未实测。

连接管理器已回放模拟 180 天持续离线、多次 32 位毫秒计数回绕、双通道后续恢复。该结果只说明连接管理器的逻辑边界；整机另有 **平台持续离线约 25 小时主动复位** 策略，不能声称整机在该模拟中持续运行 180 天未复位。

盲区容量为 9900 条，满环会覆盖最旧记录。这是有界存储策略，不能保证无限离线不丢数据。仅按 30 秒一个事件计算约容纳 82.5 小时；拐角、告警和状态变化会缩短时长。

里程正常脏数据周期保存间隔为 10 分钟，失败后按 30 秒重试，并在部分睡眠/掉电事件尝试保存。**突然失去全部供电仍可能损失最近未提交里程；当前离线主动复位路径也没有独立的最终里程保存步骤。** 这与“无定位不得凭漂移增加里程”是不同问题。若要求任何复位后里程零回退，应统一受控复位保存策略，并设计独立里程增量日志和足够的掉电保持时间；现有候选不能宣称已经满足零回退。

## 7. 尚未闭环的风险和解决方案

### 7.1 本地 JT808 平台会误解标准 0201，应在联调前修复

使用候选生产协议代码生成的真实 0201 字节，直接送入本地 `test-platform/server.js` 的位置解析器，未启动监听或打开数据库。当前 0201 路径将请求流水号误当报警字段，并按盲区上报入库。合成测试点本应为纬度 10、经度 20，实际错误解析为纬度 -0.131224、经度 2524.971313；跳过前两字节后解析正确。

同一解析器还有三个已复现问题：南/西半球状态位互换；缺少里程 TLV 时产生 0；非法 BCD 日期被 Date.UTC 归一化为有效时间。这些会制造错误轨迹、伪里程回退或错误时间，不能归咎于设备 GNSS。

解决方案：将 0201 按“应答流水号 + 位置体”处理并关联待查询事务；不要记为盲区。纠正符号位、严格校验 BCD/日历/坐标范围，缺失里程使用明确缺失状态，不能默认 0。补充 0104 参数应答接收和查询事务验证；当前平台未提供完整 8103/8104/8106/8107 参数闭环。本轮未修改平台运行代码或数据库。

### 7.2 硬件资料冲突：原始图纸支持源码，实际板号仍待对应

用户本轮提供的 AGENTS.md 写 ACC=PA3、车辆 ADC=PA0；当前源码写 ACC=PA12（低有效）、车辆 ADC=PA3、PA0 为光感中断。

已核对 `comm_board/A300-T9原理图.pdf` 原始第 1 页 U5：PA12/33 脚连接 M_ACC_IN，PA3/13 脚连接 CAR_ADC，PA0/10 脚连接 GUANG_INT；与当前源码一致。原图还标注 PD14/PD15 为 I2C SDA/SCL，PB6 为 GPS_EN、PB7 为 GPRS_DTR。

因此不能按 AGENTS.md 的简略基线直接改 GPIO，也不能在未核对目标设备板版时认定代码适配完成。解决方案是按实际板号、原图和通断/电平测量确认基线，再同步开发指南；本轮保留现有引脚及外设初始化。

### 7.3 当前镜像默认浅睡眠

本次编译未定义 `A300_STOP1_SLEEP=1`，两个生产源码文件默认值均为 0。当前为浅睡眠 WFI/SysTick 工作配置，不能声称已实现或验证 STOP1 微安级静态功耗。

若产品要求深睡眠，应单独冻结配置，再验证 RTC/ACC/Gsensor 唤醒、外设恢复、计时、定位恢复延迟和电流，并重新执行容量/栈审计。不能把切换宏当成已经完成低功耗适配。

### 7.4 FOTA 文档与实现契约不一致

AGENTS.md 描述设备 API 使用 X-Device-Key；当前固件和后端实现为设备 ID/型号/版本检查、任务下载 URL token、进度 X-OTA-Token，设备检查端点允许匿名访问。当前回放验证的是实际任务 token 路径，没有验证 X-Device-Key。

这是一项明确的规格/实现冲突。本轮未替换鉴权方式，也未部署或请求真实服务。发布前应冻结唯一契约，同步设备、后端、代理和文档，并在隔离部署环境验证拒绝路径、产品匹配、Range、并发及审计记录。后端下载使用整文件读入及后缀复制，大规模并发的内存开销还需专项负载评估。

### 7.5 资源和剩余稳定性

Flash 剩余 160 B，RAM 仅比强制间隙多 96 B。当前不能直接再移植此前两套完整功能包；继续沿用上轮“最小子集适配、先腾资源”的结论。

优先事项是：修复平台解析；核对板版和目标睡眠模式；为网络事务去阻塞及受控复位里程保存腾出资源；随后执行实机业务验证。独立里程日志、故障保留区或更大算法状态会涉及持久化/链接布局与升级兼容，须单独设计和验证，不能在本次小容量修复中仓促叠加。

ADC/I2C 等部分外设轮询仍依赖系统 tick 超时，但没有循环内持续喂狗；tick 和外设同时异常时依赖 IWDG 兜底，不能保证调用优雅返回。器件异常恢复时间和复位后的总线恢复需要 HIL。
