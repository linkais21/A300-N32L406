# JT808 栈占用优化设计

## 背景与目标

实机启动后的高水位日志为 `STK_PEAK=4436 RAM_GAP=344`，且 `HEAP_USED=0`，说明风险来自同步调用链的栈叠加。编译器栈报告也显示 RX 解析、配置保存、认证组帧和转义发送各自包含 512～1024 字节局部对象。

目标是在不改变 JT808 会话、重试、Flash 原子保存和双链路语义的前提下，移除这些大局部对象，并用构建门禁阻止回归。

## 设计

1. RX 仅为主链路 CH0 和备链路 CH3 各保留一个 512 字节重组缓冲。通道通过显式映射取槽，其他通道直接忽略。
2. 帧在所属 RX 缓冲中正向原地反转义。输出位置不会超过输入位置，解析期间 body 指针仅在同步处理函数内有效。
3. 注册成功响应只写入每链路一个待处理认证事务：认证码、链路 generation 和 pending 标志。回调中不写 Flash、不发送认证。
4. 主循环先同步链路，再处理待认证事务。generation 或链路状态失效时丢弃；Flash 保存失败时进入现有拒绝/超时路径；保存成功后更新 RAM 配置并发送认证。重复注册响应因原注册事务已被消费而不会重复排队。
5. JT808 组帧和转义输出使用一个静态工作区。显式 busy 标志限定同步、不可重入所有权；获取失败返回发送失败，不覆盖正在使用的数据。工作区在所有返回路径释放。
6. `cfg_set_auth_code` 使用受保护的静态候选配置，不再在调用栈复制完整配置；保存失败不修改当前配置。
7. 栈门禁用 ARM GCC 的 `.su` 真实结果检查关键函数，不采用源码字符串推断。

## 验收

- CH0/CH3 分片、粘包和 generation 重置互不影响；非 JT808 通道不占缓冲。
- `jt808_on_recv()` 内不发生 Flash 保存和认证发送；`jt808_process()` 才执行二者。
- 覆盖重复响应、Flash 失败、TX busy/失败、断链和 generation 变化。
- 关键函数静态栈帧均不超过门禁阈值；现有 JT808、身份、Flash 和盲区回归通过。
- 固件与 bootloader 构建、release guard、RAM guard 通过。
- 实机重新启动后仍能 REGISTER/AUTH/ONLINE，且 `RAM_GAP` 明显增大；此项必须 HIL 验证。
