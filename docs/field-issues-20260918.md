## 1. 主、副端口联动：已修复代码，待实机确认

日志第 159、209 行记录 `0x8103 result=0`，随后主、副连接分别同时使用 6666、4444 端口。第 414 行的 `IP=Success!` 后，主端口变为 9999，副端口保持 7018。

当前 `f39_config_adapter.c` 中短信 IP/FIP 的写入已经独立；实际联动来源是 `jt808_params.c` 对参数 0x0018 执行了主、副端口共同赋值。不能把日志中的这一序列归因于短信解析器。

按用户要求的独立端点语义，0x0018 现在仅更新主端口；副端口由 FIP 配置。该行为取代头文件此前声明的 shared TCP port 语义：平台如果依赖 0x0018 同时设置两个端口，需改用 FIP 指令设置副端点。副地址 0x0017 的处理不变。

回归增加了副端口保留、端口单独更新时副鉴权保留、持久化重载及重复设置不重复保存的检查。修复前在副端口保留断言失败，修复后通过。

## 2. 日志平台短信指令：已接通接收与 Pass 执行路径，待实机验证

Excel 明确列出 SMS、串口及 JT808 0x8300 三种通道；它本身没有定义日志平台 UDP 的短信指令封装。需要确认用户平台实际使用 0x8300，还是二进制通用配置中的字符串 `Pass`（历史 N32G452 实现存在此适配）。

当前 L406 通用配置链路已补上 UDP QIRD 接收、响应复制和 Pass 执行入口，并修正 IMEI BCD 编码。设备收到 `Pass` 配置后会复用现有 F39 文本执行器；只有执行成功才发送 0x14 确认。

此前链路存在以下问题：

1. `ec800m_udp_txn()` 仅发送后关闭连接，不读取响应；异步包装最终仍调用此接口。
2. `cfg_query_id()` 将 15 位 IMEI 的补零放在最后半字节；Word 协议要求放在最前半字节。
3. `cfg_query_process()` 只检查 0x92 帧外壳，没有执行 DATA 中的 Pass 指令，便尝试发送 0x14 成功确认。
4. 当前启动查询是单次路径；协议要求超时后有限重试，最多 3 次。

现已实现有界 UDP 收发、正确 BCD 身份、复用已有 F39 执行器及成功后确认；仍需覆盖真实平台响应、超时重试和设备现场状态。

Word 文档的主表使用 0x13/0x92/0x14，末尾流程说明却使用 0x11/0x12，存在文档内部冲突；当前代码和历史实现使用前者，需以实际平台报文确认。

## 3. 静止坐标漂移：确认没有锁点，尚未修改阈值

日志共有 25 条 GPS-DRIFT：2 条未知状态、4 条静止候选、19 条未满足静止条件；全部 use=0，没有 s=3。非未知状态的加速度窗口峰峰值为 22～81 LSB，候选最长 1351 ms。

当前锁点要求 5 个间隔至少 200 ms 的样本窗口，峰峰值不超过 30 mg（约 30.72 LSB），并连续满足 30 秒；60 mg（约 61.44 LSB）达到运动解锁条件。现场窗口频繁越过这两个阈值，所以零速并不等于坐标已经锁住。b=a2 是累计阻断位（定位失效、加速度运动、窗口不稳定），不能解读成每个采样时刻同时存在三个故障。

需确认截图设备是否全程固定，并采集固定/起步/低速移动对照样本后确定抗噪策略。现有日志为低频窗口快照，不能重建每个 200 ms 采样。既有 host 测试也证明零速且窗口跨度 40 LSB 时不会锁点；该测试通过是当前行为证据，并不是漂移修复通过。
